# Frontend Data/Cache Notes

## Каноническая документация

Для общих контрактов frontend/backend не дублировать правила в нескольких файлах.

- Слайдеры и промо-блоки главной: [`services/backend/docs/HOME_SLIDERS.md`](../../services/backend/docs/HOME_SLIDERS.md).
- Документ по слайдерам является источником истины для Filament, API, SSR и CSR.

Если реализация расходится с этим контрактом, расхождение нужно либо исправить в коде, либо явно отметить как переходное состояние в каноническом документе. Не создавать ещё одну независимую инструкцию рядом с frontend-компонентами.

## SWR and SSR contract

- SSR и CSR должны использовать одинаковые API-контракты и query-параметры. Нельзя получать один и тот же блок страницы из разных endpoint'ов на сервере и в браузере.
- Для каталога/поиска должны совпадать `sort_by`, `sort_order`, `per_page`, `attributes[...][]`.
- Все регионозависимые ключи SWR обязаны включать регион (`region_id`), включая home-блоки товаров и корзину.
- Для SSR fallback используются ключи из `src/utils/ssr-to-swr.ts`; ручные строковые ключи стоит избегать.

## Homepage promo / sliders

- Система слайдеров одна; место записи определяется `placement` + `slot`.
- Целевой единый источник данных для SSR и CSR — `GET /api/v1/sliders`.
- `/api/v1/sliders/home` пока существует как переходный агрегатор и не должен становиться новым отдельным контрактом; детали и план удаления описаны в `HOME_SLIDERS.md`.
- Frontend не должен подменять отсутствие production-данных скрытыми demo-акциями. Если активных записей нет, соответствующая зона не рендерится.
- Демо-контент для разработки должен создаваться в backend/БД, чтобы он был виден и управляем из Filament.

## Cart and counters

- Корзина перезагружается через key-driven SWR (`/api/cart?region_id=...`), без дополнительных listener-дублей.
- Счётчики (`cart/wishlist/compare`) обновляются по фокусу/visibility и на умеренном интервале, чтобы снизить лишнюю сетевую нагрузку.
- Оптимистичный UI не является заменой серверной защите от гонок. Изменения одной позиции корзины должны сериализоваться, а итоговое подтверждённое состояние — сверяться с backend.

## Product page

- PDP использует SWR для `stock-settings`, `reviews` (ленивая загрузка по вкладке), `related`.
- Состояние wishlist/compare берётся из централизованного хука `useWishlistAndCompare`, без прямых list-запросов со страницы.
