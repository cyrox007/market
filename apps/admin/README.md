# Прототип новой админ-панели

Отдельный React-прототип новой админки проекта «Светофор Мебели».

Прототип всегда строится от актуального `develop`. Текущая база прототипа: `41be4940614f77b4226eaca8c90ec9cbe3fc65fa`.

## Главная цель

Не переносить Filament один в один, а улучшить ежедневную работу оператора каталога.

Основные принципы:

- минимум прокрутки страницы;
- отдельные рабочие области с собственной прокруткой;
- крупные смысловые вкладки;
- длинные формы при необходимости делятся на понятные шаги;
- обязательные поля явно помечены;
- заполненность карточки показывается до сохранения;
- ошибки проверки собраны в одном месте и ведут к конкретному полю;
- редкие поля SEO/1С не мешают ежедневному редактированию;
- категории и комнаты показаны как две разные структуры;
- характеристики сгруппированы по смыслу, а не одной длинной простынёй;
- вариации, остатки, медиа и связи имеют отдельные рабочие экраны.

## Что есть в прототипе

- светлая и тёмная темы;
- стилевое направление на основе админки `cyrox007/vrn-history`;
- рабочее место каталога: дерево разделов → список товаров → редактор;
- переключение «Категории / Комнаты»;
- редактор товара по реальной структуре актуального `develop`;
- индикатор заполненности;
- сводка ошибок и рекомендаций;
- пошаговый раздел «Основное»;
- крупные вкладки:
  - Основное;
  - Характеристики;
  - Вариации;
  - Остатки;
  - Медиа;
  - Связи;
  - SEO / 1С.

Данные пока демонстрационные. Backend не меняется.

## Запуск

Из корня репозитория:

```bash
npm install
npm run dev --workspace=svetofor-admin-prototype
```

После запуска:

```text
http://localhost:5174
```


## Ограничения архитектуры по результатам аудита

Новая админка не должна переносить существующее поведение Filament один в один. Аудит текущей реализации выявил проблемы, которые необходимо устранять на уровне backend и сценариев работы, а не маскировать новым интерфейсом.

### Права доступа

- право «просматривать» не должно автоматически разрешать изменяющие или опасные операции;
- каждое действие изменения состояния должно иметь отдельную серверную проверку права;
- сервисные и административные команды не должны становиться доступны только потому, что пользователь может открыть страницу.

### Заказы, оплаты и возвраты

- операции создания заказа, изменения статусов, списания остатков, оплаты и возврата должны быть целостными серверными сценариями;
- защита от повторного списания или повторного возврата не должна зависеть от памяти одного PHP-процесса;
- интерфейс не должен предлагать действие, которое сервисный слой фактически не поддерживает;
- изменение составляющих доставки и других ценовых параметров должно сопровождаться серверным пересчётом итогов заказа.

### Импорт и 1С

- импорт из 1С рассматривается как отдельный рабочий процесс, а не как скрытая кнопка внутри большой формы товара;
- импорт не должен сначала самостоятельно сохранять сущность, а затем повторно запускать сохранение всей формы;
- ошибки импорта, конфликтующие значения и результат операции должны быть явно показаны оператору;
- длительные операции следует отделять от обычного HTTP-сохранения формы.

### Граница UI и бизнес-логики

- React-интерфейс не должен содержать расчёты и правила предметной области, которые должны жить в backend;
- новая админка должна обращаться к явным административным API/командам;
- успешное отображение формы не считается доказательством корректности бизнес-операции;
- для опасных действий нужны серверная проверка, понятное подтверждение и однозначный результат операции.

### UX-следствия аудита

- недоступное действие лучше не показывать, чем показывать кнопку, которая затем падает;
- действия с необратимыми или денежными последствиями должны быть визуально отделены от обычного редактирования;
- ошибки сервиса должны переводиться в понятное оператору сообщение без потери технического контекста для диагностики;
- многошаговые операции должны показывать текущий этап, результат каждого этапа и возможность безопасного повторения там, где это допустимо.
