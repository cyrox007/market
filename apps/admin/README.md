# Новая админ-панель

React-прототип новой административной панели проекта «Светофор Мебели».

Ветка строится от `develop`.

## Как она запускается

Рабочий сценарий — **сборка в OpenServer**, а не отдельный Vite dev-server.

Команда из корня репозитория:

```cmd
npm run admin:build
```

Vite складывает готовую сборку прямо сюда:

```text
services/backend/public/admin-ui
```

Открывать:

```text
http://svetofor.local/admin-ui/
```

Админка и Laravel после сборки находятся на одном origin `svetofor.local`. Поэтому используются существующая web-сессия Filament, обычные cookies и CSRF без проксирования через `localhost:5174`.

`npm run dev --workspace=svetofor-admin-prototype` можно использовать только для работы над внешним видом. Для проверки авторизации и реальных данных использовать сборку OpenServer.

## Подготовка после обновления ветки

```cmd
git fetch origin
git switch admin/react-prototype
git reset --hard origin/admin/react-prototype

cd services\backend
php artisan migrate
php artisan optimize:clear
cd ..\..

npm install
npm run admin:build
```

После этого открыть:

```text
http://svetofor.local/admin-ui/
```

Если административной сессии нет, интерфейс покажет экран входа. Войти через:

```text
http://svetofor.local/admin_sv/login
```

После входа вернуться на:

```text
http://svetofor.local/admin-ui/
```

## Важно

Это не демонстрационные данные.

Прототип работает с локальным Laravel backend и локальной БД:

- товары — реальные;
- категории — реальные;
- комнаты — реальные;
- характеристики и значения — реальные;
- заказы — реальные, пока только чтение;
- магазины — реальные;
- локации — реальные;
- склады — реальные.

Изменение основной карточки товара и настроек характеристики сохраняется в реальную локальную БД.

## Что уже сохраняется

### Товар

Через защищённый `/admin_sv/api/products/{id}`:

- название;
- SKU;
- GTIN;
- описание;
- статус;
- приоритет;
- цена;
- цена до скидки.

Запись проходит через `ProductPolicy::update` и Laravel validation.

Характеристики, вариации и складские остатки товара уже читаются из БД. Изменение этих связей пока не включено.

### Характеристика

Через защищённый `/admin_sv/api/attributes/{id}`:

- название;
- slug;
- тип;
- участие в вариациях;
- использование в фильтрах;
- обязательность;
- множественность;
- разрешение ручного значения;
- порядок.

Запись проходит через `AttributePolicy::update`.

Значения характеристики пока доступны для чтения.

### Заказы

Заказы и состав читаются через административный endpoint с `OrderPolicy::viewAny`.

Изменяющие операции пока не подключены. По аудиту сначала нужно исправить серверную целостность возвратов, списания остатков, повторных действий и пересчёта итоговой суммы.

## Склады

Для складов добавлены отдельные разрешения:

- `viewAny warehouses`;
- `view warehouses`;
- `create warehouses`;
- `update warehouses`;
- `delete warehouses`.

И отдельная `WarehousePolicy`.

Разрешения создаёт миграция:

```text
2026_09_23_113000_add_warehouse_permissions.php
```

## Архитектурные правила по результатам аудита

Новая админка не переносит поведение Filament один в один.

- право просмотра не разрешает изменение;
- каждое изменение повторно проверяется backend;
- скрытие кнопки в React не заменяет Laravel Policy;
- денежные и необратимые операции не реализуются только в UI;
- расчёты и правила предметной области остаются в Laravel;
- изменение доставки должно приводить к серверному пересчёту итогов;
- защита от повторного списания или возврата не должна храниться только в памяти процесса;
- импорт из 1С должен быть отдельным рабочим процессом;
- ошибки backend должны быть понятны оператору, но не скрывать диагностическую информацию.

## UX-принципы

- минимум прокрутки всей страницы;
- отдельные рабочие области со своей прокруткой;
- крупные смысловые блоки и вкладки;
- обязательные поля видны сразу;
- ошибки показываются рядом с рабочей областью;
- недоступные по правам действия не предлагаются оператору;
- редкие и опасные действия отделяются от ежедневного редактирования.
