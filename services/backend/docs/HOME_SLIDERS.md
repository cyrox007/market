# Слайдеры главной — единый контракт

Этот документ — **единственный актуальный источник правил для промо-блоков главной страницы**. Он описывает модель данных, настройку в Filament, соответствие макету и контракт с frontend/SSR.

> Важно: это **одна система слайдеров**, одна таблица `sliders` и один раздел админки. `placement` и `slot` определяют, в каком месте главной показывается запись.

## 1. Что есть на главной

Главная использует четыре визуальные зоны:

| Зона в макете | `placement` | `slot` | Количество активных записей | Mobile |
|---|---|---|---|---|
| Большая карусель слева сверху | `top` | `main` | несколько | показывается |
| Маленькая карточка справа сверху | `top` | `right_top` | ровно одна | скрыта |
| Маленькая карточка справа снизу | `top` | `right_bottom` | ровно одна | скрыта |
| Нижний широкий баннер-слайдер | `bottom` | `main` | несколько | показывается |

Для `right_top` и `right_bottom` действует взаимоисключение: если включить новую запись в той же позиции, предыдущая активная запись этой позиции автоматически выключается.

Для `bottom` модель всегда нормализует `slot=main`; отдельного выбора позиции в форме нет.

## 2. Как собрать экран из макета

Чтобы получить композицию как на текущем макете главной, создаются **отдельные записи**.

### Большой верхний слайд

Пример: **«Сборка в день доставки»**.

- Какой блок редактируем: `Верхний блок — большой слайдер и две карточки справа`.
- Куда поставить: `Большой слайдер слева`.
- Порядок показа: `0`, `10`, `20` и т. п.; меньшее число показывается раньше.
- Заголовок: `Сборка в день доставки`.
- Описание: обычный текст, переносы строк допустимы.
- Ссылка: необязательна; если задана, кликабельным становится весь слайд.
- Отдельной CTA-кнопки в текущем макете нет.
- Основное изображение: ориентир **824×461 px**.
- Для телефона желательно отдельное изображение с кадрированием примерно **4:5**.

### Правая верхняя карточка

Пример: **«Кредит и рассрочка»**.

- Блок: верхний.
- Позиция: `Маленькая карточка справа — сверху`.
- Метка: `Выгодно`.
- Цвет метки: `Жёлтый`.
- Заголовок: `Кредит и рассрочка`.
- Описание: короткий обычный текст.
- Ссылка: обязательна.
- Текст кнопки/ссылки: обычно `Подробнее`.
- Основное изображение: ориентир **400×222 px**.
- На mobile эта карточка не показывается.

### Правая нижняя карточка

Пример: **«Гарантия честной цены»**.

Настройки такие же, как у `right_top`, но позиция — `Маленькая карточка справа — снизу`. Для текущего макета метка `Гарантия` использует зелёный тон.

### Нижний широкий баннер

Пример: **«Спальня, в которую хочется»**.

- Какой блок редактируем: `Нижний блок — широкий баннер-слайдер`.
- Дополнительная позиция не выбирается: backend сохраняет `slot=main`.
- Порядок показа задаёт порядок слайдов.
- Метка используется как надзаголовок/период акции, например `1 — 30 сентября`.
- Заголовок и описание — обычный текст.
- Ссылка обязательна.
- Текст кнопки обычно `Подробнее`.
- Основной desktop-кадр: ориентир **1440×260 px**.
- Для телефона желательно отдельное изображение, подготовленное под узкий экран.

## 3. Поля формы Filament

Раздел: **Контент → Слайдеры главной**.

### Расположение

- `placement` — верхний или нижний блок;
- `slot` — роль записи в верхнем блоке;
- `priority` — порядок только для зон, где допустимо несколько материалов (`top/main`, `bottom/main`);
- `is_active` — показывать запись на сайте.

### Содержимое

- `title` — обязательный заголовок;
- `slug` — системный адрес записи, не определяет место на главной;
- `description` — **обычный текст**, не HTML; переносы строк сохраняются;
- `link` — куда ведёт материал;
- `button_text` — используется правыми карточками и нижним баннером.

Старые записи могли содержать HTML от прежнего RichEditor. `SliderResource` нормализует такое описание в plain text перед выдачей API.

### Промо-метка

- `badge_text` — текст метки/периода;
- `badge_tone` — цвет капсулы для правых карточек: `red`, `yellow`, `green`.

Поля `badge_link` и `badge_icon` остаются в модели/API ради совместимости со старыми данными, но текущий макет главной на них не опирается.

### Изображения

Приоритет источников:

1. MediaLibrary upload;
2. `image_url` / `mobile_image_url` как временный fallback.

Если отдельное mobile-изображение не задано, API использует desktop-изображение.

## 4. Источник истины

Источник контента в production:

```text
Filament
  ↓
таблица sliders
  ↓
SliderResource
  ↓
API
  ↓
SSR и браузерный frontend
```

Frontend **не должен хранить собственные production-акции**. Если в базе нет активного материала для зоны, эта зона должна отсутствовать на странице.

Демо-данные допустимы только как явно созданные записи в БД (seeder/локальная разработка), чтобы оператор видел их в Filament и мог редактировать или выключить.

### Демо-seeder

```bash
php artisan db:seed --class=SliderDemoSeeder
```

Seeder идемпотентный и создаёт демонстрационные записи для всех четырёх зон. В local/testing он может использоваться для разработки.

**Не использовать frontend fallback как замену отсутствующим данным backend в production.**

## 5. API: принятое архитектурное решение

Для новых потребителей каноническим должен быть существующий endpoint:

```http
GET /api/v1/sliders
```

Без параметров он должен отдавать все активные материалы главной, а frontend сам группирует их по `placement` + `slot`.

Фильтры остаются опциональными:

```http
GET /api/v1/sliders?placement=top
GET /api/v1/sliders?placement=bottom
GET /api/v1/sliders?placement=top&slot=main
GET /api/v1/sliders?placement=top&slot=right_top
GET /api/v1/sliders?placement=top&slot=right_bottom
```

### Переходное состояние на 2026-10-05

В коде пока существует дополнительный агрегирующий endpoint:

```http
GET /api/v1/sliders/home
```

и текущий frontend использует его для главной. Это **переходная совместимость, а не второй источник данных**: endpoint читает ту же таблицу `sliders`.

Принятое направление:

1. перевести CSR и SSR главной на один `GET /api/v1/sliders`;
2. без параметров возвращать весь набор `top` + `bottom`;
3. группировать данные на frontend по `placement` и `slot`;
4. после миграции удалить `/sliders/home`;
5. не добавлять новых потребителей `/sliders/home`.

Пока эти изменения не внесены в код, документация должна явно отличать **целевой контракт** от **переходного состояния**, чтобы не создавать ложное впечатление о двух независимых системах.

## 6. Формат элемента API

```json
{
  "id": 1,
  "placement": "top",
  "slot": "main",
  "title": "Сборка в день доставки",
  "description": "Привезём, соберём и уберём упаковку.",
  "link": "/delivery",
  "button_text": null,
  "badge_text": null,
  "badge_link": null,
  "badge_icon": null,
  "badge_tone": "yellow",
  "image": "/storage/...",
  "image_thumb": "/storage/...",
  "image_hd": "/storage/...",
  "image_fullhd": "/storage/...",
  "image_mobile": "/storage/...",
  "image_mobile_thumb": "/storage/...",
  "image_mobile_hd": "/storage/...",
  "image_mobile_fullhd": "/storage/...",
  "priority": 0
}
```

Frontend не должен определять расположение по `priority`, названию или порядку массива. Для расположения используются только `placement` и `slot`; `priority` определяет порядок внутри многослайдовой зоны.

## 7. Что нельзя делать

- Не создавать отдельную таблицу/модель для нижнего баннера.
- Не определять правую верхнюю/нижнюю карточку по индексу массива.
- Не использовать `slug` или заголовок для определения зоны.
- Не хранить production promo-контент только во frontend.
- Не показывать демо-акции пользователю только потому, что API вернул пустой список.
- Не делать отдельные независимые схемы загрузки данных для SSR и CSR.

## 8. Проверка после настройки

Минимальная проверка перед публикацией:

1. в Filament видны все активные материалы и их позиции;
2. `top/main` листается в порядке `priority`;
3. `right_top` и `right_bottom` занимают именно свои фиксированные позиции;
4. на mobile две правые карточки скрыты;
5. mobile-картинка используется, если загружена;
6. нижний баннер получает CTA и порядок из админки;
7. отключение записи в Filament убирает её с сайта;
8. отсутствие записей не вызывает появление скрытого frontend demo-контента;
9. SSR и CSR показывают один и тот же набор данных без подмены после гидрации.

## 9. Совместимость старых записей

Старые записи после миграции получают:

```text
placement = top
slot = main
```

Это сохраняет существующие записи большой верхней карусели. Перед публикацией оператор должен вручную проверить, какие старые записи действительно должны остаться активными.
