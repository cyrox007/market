# Контракт ФИО пользователя

## Модель данных

Таблица users сохраняет обязательное поле name для старых клиентов.
Поля first_name, last_name, patronymic добавлены как nullable.
Миграция НЕ изменяет и НЕ разбивает существующие значения name.

Подтверждённые части имени используются для формирования отображаемого name
в порядке «Фамилия Имя Отчество». Отчество необязательно, составные имена
и фамилии хранятся целиком. Гадать части по пробелам запрещено.

## API

POST /api/v1/auth/register принимает либо:
- legacy: name, email, password, password_confirmation, phone;
- новый формат: first_name, last_name, необязательный patronymic,
  email, password, password_confirmation, phone.

Передавать name одновременно с first_name/last_name/patronymic нельзя.
Формат нельзя смешивать. GET /api/v1/auth/me, POST /auth/login,
POST /auth/register, PUT /auth/profile сохраняют исходные поля и дополнительно
возвращают три nullable компонента ФИО.

PUT /api/v1/auth/profile:
- имя в одной строке: name;
- раздельное ФИО: first_name и last_name, patronymic (необязательно);
- смена только телефона: phone.

При частичном обновлении раздельных полей имя и фамилия могут браться
из уже сохранённой структуры, но обе части обязаны быть непустыми.
Для существующего legacy-пользователя раздельные поля впервые заполняются
только им самим (нельзя автоматически нарезать прежний name).
Изменение name старым клиентом сбрасывает структурированные части,
чтобы избежать устаревших данных. Формируемое полное ФИО: не более 255 символов.

## Гостевой заказ и 1С

Существующий контакт заказа orders.contact_name сохраняется отдельно.
Автоматическая регистрация при заказе продолжает создавать пользователя
с legacy name и незаполненными структурированными полями.
Передача контактного ФИО в 1С и существующие заказы не меняются.

## Развёртывание

Сначала применить миграцию и обновить API, затем выкатывать новый фронтенд.
Старые клиенты могут продолжать использовать единое поле name.
Проверки: AuthControllerTest, profile-name.test.ts.
