# Рабочая панель Filament: ролевой дашборд (23.11.2026)

## Цель

Главная `/admin_sv` должна помогать сотруднику принимать решения: показывать задачи, не требовать доступа к чужим данным и не смешивать показатели разных единиц измерения.

Проект меняет **только Laravel / Filament**. React/SSR (`apps/frontend`) не изменяются. Развёртывание и слияние — только после ревью отдельного PR.

## Компоновка

Файл `App/Filament/Pages/Dashboard.php` заменяет стандартный Filament Dashboard. В `AdminSvPanelProvider` сохраняется автообнаружение страниц. Сетка адаптивная: один столбец на узких экранах и два на широких. Порядок (запрещённые виджеты Filament скрывает до загрузки):

1. **Активность сотрудников (только admin/super_admin)**: текущий раздел каждого присутствующего пользователя, просмотр или редактирование карточки, количество вкладок и последнее подтверждение. Обновляется без перезагрузки каждые 30 секунд; сведения доступны только руководящим ролям и фильтруются повторной проверкой прав на ресурс.
2. **Требуют внимания**: не только свежие заказы, но и давние необработанные, ошибки интеграции, обращения на отмену, незавершённые возвраты; ссылка ведёт к просмотру/редактированию по фактическим правам.
2. **Очереди заказов**: новые, в обработке менеджера, сборка, готовые к отгрузке — кликабельные ссылки на фильтр `status`.
3. **Динамика оформлений**: количество заказов за 14 дней, отдельная шкала в штуках. Отменённые учитываются как факт создания заказа.
4. **Стоимость заказов**: только для администратора с разрешением на заказы. Сумма неотменённых заказов по дате их создания. **Не отображается под названием «Выручка»**: подтверждённые платежи и частичные возвраты не равны этой сумме.
5. **Карточки требуют внимания / контент / пользователи**: отдельные причины, сгруппированные по критичности; вместо суммарных счётчиков каталога.

У отсутствующих задач — нули и штатное пустое состояние таблицы. Виджеты имеют раздельные запросы и короткий кэш (90–120 секунд); отсутствие разрешения предотвращает загрузку данных чужого раздела.

## Разрешения

`DashboardRoleChecks` проверяет **эффективные** разрешения `viewAny orders`, `viewAny products`, `viewAny users`, `viewAny articles`, `viewAny sliders`, `viewAny newsletter_subscribers`. Контентный виджет отдельно проверяет право перед каждой метрикой.

Финансовые суммы доступны только `admin` / `super_admin` **при наличии** `viewAny orders`: специального разрешения на платёжную аналитику сейчас нет, поэтому доступ не расширяем до всех менеджеров с правом просмотра заказов. Системный виджет Filament версии удалён с главной (его не удаляли из проекта).

Панель «Быстрые действия» убрана с главной: переходы доступны в боковом меню, создание — в соответствующих разделах.

## Ограничения первого этапа

- Сумма оформленных заказов **не равна оплаченной выручке**. Перед реализацией отчётности по реальным поступлениям нужно сверить статусы платёжных шлюзов, возвраты и временные зоны.
- Количество товара с флагом `backorder` не равно текущему наличию: карточка явно сообщает, что это разрешение предзаказа.
- «Без собственных изображений» — это диагностический признак. Вариации могут наследовать фотографии родителей.
- Для блока «Требуют внимания» используется текущее состояние заказа/интеграции/возвратов, а не отдельная таблица задач.
- В этом PR не создаются новые роли и permissions и не меняются workflow, заказ, остатки, доставка или публичный API.
- Персональная настройка виджетов и отдельная финансовая сводка по подтверждённым платежам — будущие улучшения.

## «Карточки требуют внимания» (добавлено 23.11.2026)

Основной виджет каталога теперь показывает **проблемные карточки**, конкретные причины, тип карточки
(самостоятельный товар / родитель вариаций / торговое предложение / комплект),
ссылку «Редактировать» при наличии права и дату последней полной проверки.
Критичные проблемы идут первыми, затем большее число замечаний. Счётчики
«Критично» и «Несколько замечаний» открывают фильтры полного read-only списка в
разделе «Товары». На главной максимум 5 карточек.

Критерии: (1) отсутствующая положительная базовая цена продаваемого SKU;
(2) отсутствующее главное изображение в коллекции Spatie `images`, включая
наследование предложения от родителя и родителя от активного предложения;
(3) нет активных предложений у вариативного родителя;
(4) нет своей/родительской категории;
(5) пустой или дублирующийся `external_id` у продаваемой позиции,
**но не у виртуального родителя вариаций**; текущая таблица `products`
имеет уникальный индекс по `external_id`, поэтому дубликаты являются защитной
проверкой для старых/нарушенных данных, а не обычным сценарием сохранения;
(6) пустое HTML-описание с учётом `getEffectiveDescription()`;
(7) создана строка цвета без `color_solution_id` либо выбранного объекта;
(8) отсутствует физическая миниатюра главного изображения после 30 минут
на обработку. **Важно:** в текущей схеме `product_color_rows.color_solution_id` —
NOT NULL; незавершённая строка не сохраняется штатным интерфейсом. Проверка цвета
предназначена для устаревших/нарушенных импортированных данных; ограничение БД
не ослабляем. Отсутствующий оригинал — критическая ошибка; при недоступности
диска запуск считается неуспешным, а предыдущая завершённая проверка сохраняется.

Порог: **любая одна критическая проблема** или **как минимум два предупреждения**.
Все причины для попавшей в список карточки показываются отдельно, без баллов.
Нулевой остаток, отсутствие скидки, отзывов и вручную заполненного SEO **не проверяются**.
Цена не рассчитывается по региону/клиенту: используется хранимая базовая цена
продаваемого SKU; для виртуального родителя она не обязательна.
Это диагностика целостности каталога, а не проверка окончательной цены заказа.

### Фоновый проход и свежесть

```bash
cd services/backend
php artisan migrate --force
php artisan catalog:audit-cards                     # первый проход вручную после развёртывания
php artisan catalog:audit-cards --skip-files        # диагностика без обращения к файловым дискам
```

`routes/console.php` запускает полный аудит **ежедневно в 03:30** через Laravel Scheduler
при настроенном `schedule:run`. Проход работает пакетами по 100 товаров и с
распределённой блокировкой `catalog-card-audit`; доступ к файловым дискам
осуществляется только из команды. Дашборд не сканирует изображения и не
пересчитывает диагнозы: он читает только **последний полностью завершённый**
снимок. Ошибки сканирования сохраняют старый снимок, а новое состояние не
публикуется как частично готовое. После нового успешного прохода старый снимок
удаляется, чтобы не накапливать историю.

**Примечание по свежести:** изменение карточки после последнего аудита
не сразу обновит показатели — дата проверки отображается явно.
Данные с нуля появятся только после первого успешного запуска фоновой команды.
Команда не изменяет поля товаров и файлов.
