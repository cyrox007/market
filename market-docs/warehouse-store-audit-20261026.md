# Аудит складов, магазинов и доставки — 26.10.2026

> Снимок до решения о полном отключении старого контура. Последующее решение
> и реализованный новый контракт описаны в
> [warehouse-only-fulfillment.md](warehouse-only-fulfillment.md).
> Предложения сохранить совместимость ниже больше не являются планом внедрения.

## Область проверки

Админка, модели связей, API магазинов, расчёт доставки/самовывоза,
складские остатки, резервирование и фактическая конфигурация production.
Проверка production только на чтение. Данные, настройки, фронтенд и импорт
координат не изменялись. Это отчёт об аудите, не отчёт о внедрённых исправлениях.

## Главный вывод

Новая схема реализована, но не полностью настроена на production; старые
зависимости остаются в действующем checkout. Удалять старые сущности и связи
сейчас нельзя: переход адресного поиска на новый API не равен переходу
оформления заказа на расчёт доставки от склада.

## Подтверждённые проблемы

### 1. Два критерия готовности самовывоза

`StoreResource::toArray()` требует непустой адрес общей площадки, чтобы
выдать `pickup_enabled=true`. `WarehousePickup::options()` такого условия
не проверяет. При активных магазине и физическом складе на одной площадке
с пустым адресом список магазинов запрещает самовывоз, но расчёт предлагает
этот магазин как точку выдачи.

Воспроизведено изолированным тестом на SQLite. В production магазинов
пока нет, поэтому это подтверждённый дефект сценария, а не утверждение
о существующем ошибочном заказе.

Нужно единое правило готовности точки для списка магазинов, расчёта,
выбора точки и резервирования. Координаты и адрес проверять отдельно:
отсутствие координат не должно автоматически означать отсутствие адреса.

### 2. Параллельные старый и новый контуры доставки

`apps/frontend/src/pages/checkout/page.tsx` продолжает вызывать
`getLocations`, `getShippingMethods`, `getDeliveryHandlingTypes`,
`getAdditionalServices`, `calculateShippingMethod`, `calculateShipping`.
Вызовов `/shipping/quote` в исходниках фронтенда не найдено.
Старые локации также использует личный кабинет и LocationSearchInput.

`tests/Feature/Api/LegacyShippingRemovalTest.php` явно сохраняет эти маршруты
до перехода фронтенда. Поэтому «Локации» пока не являются полностью мёртвым
разделом. Удаление связей сейчас может изменить доступность и расчёт заказа.

### 3. Разные источники адреса и координат усложняют работу оператора

Есть адрес общей площадки, собственный адрес склада, старые поля магазина
и `shipping_location_id`. Общая площадка должна быть источником адреса
совместно расположенных магазина и склада; отдельная точка отгрузки склада
может отличаться от входа в магазин. Это необходимо явно различать в форме.

`PhysicalSiteSelect` обозначает площадку необязательной, тогда как
`PhysicalSiteSetup::store()` требует её при создании нового магазина.
Подсказка формы противоречит проверке сохранения. Старые магазины без
площадки допускаются ради совместимости, что не делает поле необязательным
для нового магазина.

## Дополнительные риски по коду, требующие регрессионных тестов

- Для драйверов кэша без тегов `Cacheable::flushBasicCache()` не очищает
  `store_cities` и `store_index_city_*`. Список городов/магазинов может
  оставаться старым до истечения TTL (по умолчанию 10 часов). Для Redis
  с тегами выполняется общий сброс тегов; нельзя объявлять этот риск
  подтверждённым production-инцидентом без проверки драйвера.
- В `WarehouseOrderStock::reserve()` исчезновение магазина между выбором
  и резервированием может переключить проверку на флаг самовывоза склада.
  Если в снимке заказа указан магазин, его отсутствие должно означать
  отказ с повторным выбором, а не неявную замену точки выдачи.
- Проверить единообразие запрета неактивного родителя SKU в доставке,
  самовывозе и корзине, в том числе при прямой передаче ID предложения.

Подозрение на открытие неактивного магазина по slug **не подтвердилось**:
scope Laravel группирует условия. Тест проверил 404 для выключенного и
200 после включения той же записи. Это не дефект.

## Какие разделы сохранять и какие выводить из эксплуатации

| Раздел/связь | Решение |
| --- | --- |
| Склады, остатки, профили доставки | Основной рабочий контур; оставить |
| Магазины → склад, общая площадка | Основной рабочий контур; оставить и усилить проверки |
| Типы обработки | Оставить: используются новыми тарифами WarehouseServices |
| Дополнительные услуги | Оставить: используются новыми тарифами WarehouseServices |
| Локации | Пока совместимость: действующие checkout/кабинет/поиск адреса |
| Методы доставки по регионам | Старый контур; не удалять API до перехода checkout |
| Службы доставки | Проверить/вывести вместе со старым региональным расчётом; не удалять данные раньше |
| warehouse_shipping_location | Пока совместимость складского определения доступности |
| store.shipping_location_id | Старый контур правил; убрать из основной формы после проверки правил корзины |
| profile.services_location_id | Пока совместимость тарифов; используется при service_tariffs=null |

Пустая таблица региональных методов не доказывает ненужность всего
старого контура: отдельно остаётся расчёт от локации и её правил.
Перенос старых пунктов в явно обозначенную группу совместимости возможен
без удаления данных, но это ещё не завершённая миграция.

## Порядок стабилизации

1. Единая готовность самовывоза; запрет неявной замены исчезнувшей точки.
   Тесты пустого адреса, выключенного магазина/склада, несовпадающих площадок,
   остатков SKU, изменения/удаления точки и повторного резервирования.
2. Исправить противоречивые подсказки формы и правила изменения связанного
   склада. Развести общий адрес и отдельную точку отгрузки в интерфейсе.
3. Настроить реальные адреса, общие площадки, магазины и профили по
   подтверждённым бизнес-данным. Сначала контрольный склад, затем остальные.
4. Проверить API полного сценария: список SKU → корзина → расчёт → заказ →
   резерв → отмена/возврат остатков, доставка и самовывоз отдельно.
5. Согласовать отдельную задачу перехода checkout на новый API. В рамках
   текущего аудита фронтенд не изменялся.
6. Только после перехода и проверки других клиентов убрать старые пункты,
   записи в формах и runtime-связи. Удаление таблиц — отдельная последующая
   миграция с резервной копией и проверкой исторических заказов.

  выполнялись в рамках аудита.
