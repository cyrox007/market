# Краткие товарные позиции для списка и последнего заказа (23.11.2026)

## Задача

Фронтенд ранее запрашивал полный список `GET /api/v1/orders` только ради названий и миниатюр карточек заказов.
В компактном `GET /api/v1/orders?view=compact` и `GET /api/v1/orders/summary` поле `last_order` не содержало ни одной позиции.
В этом изменении оба ответа получают одинаковый облегчённый состав без загрузки полного `ProductResource`.

## Контракт

Для каждой карточки компактного списка и `last_order`:

- `items_count` — фактическое количество строк заказа.
- `items` — **все** строки в облегченном виде, чтобы существующий `OrderSummaryRow` мог показывать все названия и правильное `+N`.
- `items_preview` — первые три строки из `items` для небольших новых виджетов.

Каждая строка содержит `id`, `product_id`, `name`, `quantity`, `price`, `total` и
небольшой объект `product: {id, name, image, thumbnail}`.
Объект `product` **не равен полному ProductResource** и не содержит остатки, доступность или правила цены.
Его `name` совпадает с сохранённым названием строки.

Пример ответа карточки:

```json
{
  "id": 123,
  "number": "ORD-123",
  "items_count": 1,
  "items": [
    {
      "id": 456,
      "product_id": 789,
      "name": "Шкаф Бруно, дуб",
      "quantity": 2,
      "price": 14500,
      "total": 29000,
      "product": {
        "id": 789,
        "name": "Шкаф Бруно, дуб",
        "image": "https://example.test/storage/1/cover.jpg",
        "thumbnail": "https://example.test/storage/1/conversions/cover-thumb.jpg"
      }
    }
  ],
  "items_preview": [
    {
      "id": 456,
      "product_id": 789,
      "name": "Шкаф Бруно, дуб",
      "quantity": 2,
      "price": 14500,
      "total": 29000,

```

Пример сокращён: настоящие карточки также содержат идентификатор статуса, итоговую сумму и `presentation`.
URL и номера здесь демонстрационные.

### Снимок заказа и особенности старых данных

- **Название** читается из сохранённого `order_items.name`, а не из сегодняшнего имени товара; `display_snapshot.name` используется при отсутствии значения строки.
- **Фотография** сейчас не фиксируется в снимке покупки. Берётся актуальная основная фотография связанного товара, а у предложения — родителя, если у SKU нет собственной. Если фото или товар более недоступны, `image` и `thumbnail` равны `null`.
- Для `thumbnail` применяется Spatie `getAvailableUrl(['thumb'])`: если конверсия ещё не создана, возвращается оригинал.
- Для старых заказов без `display_snapshot` сохранённое название строки остаётся доступным.
- `items_preview` не содержит отдельной исторической копии товаров; это первые три строки облегчённого `items`.

### Производительность и безопасность

Связи `items.product.media` и `items.product.parentProduct.media` загружаются заранее для всех заказов на **одной странице** компактной выдачи и для `last_order` в сводке. Нет запроса товара или медиа на каждый элемент. Полные отношения заказа и внутренние свойства склада не добавляются.
Логика доступа не менялась: возвращаются только заказы авторизованного владельца.

`GET /api/v1/orders` без `view=compact` остаётся обратносуместимым полным ответом.

### Использование на фронтенде

Для кабинета и списка заказов предпочтительны:

- `GET /api/v1/orders?view=compact&page=1&per_page=10` — постраничный список.
- `GET /api/v1/orders/summary` → `last_order` — последний заказ.

Можно использовать `items` напрямую с текущей разметкой `OrderSummaryRow`, не запрашивая полные `OrderResource`.
Альтернатива для мини-карточки — `items_preview` + `items_count`.
Реальное переключение frontend на эти эндпоинты находится вне этого backend PR.

### Тесты

```bash
cd services/backend

```

Проверяются: сохранённое имя после переименования продукта, наследование фотографии у SKU, `null` без изображения/товара, количество/первые три строки, отсутствие полной модели продукта, контроль прав пользователя и число SQL-запросов при изменении числа заказов.
