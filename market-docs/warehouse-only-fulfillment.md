# Доставка и самовывоз: только складской контур

Изменение контракта от 26.10.2026. Старые API намеренно удалены, даже если
старый клиент ещё вызывает их. Фронтенд в этой доработке не изменяется.

## Что удалено из рабочего контура

- `/api/v1/regions`, `/regions/tree`, `/regions/detect`.
- Все прежние `/api/v1/shipping/locations*`, `/shipping/calculate`,
  `/shipping/carriers`, `/shipping/shipping-methods*`,
  `/shipping/delivery-handling-types`, `/shipping/additional-services`.
- Страницы и доступ к ресурсам «Локации», «Службы доставки»,
  «Методы доставки по регионам» в админке.
- Старые калькуляторы, поставщики методов/обработки, калькулятор услуг
  по локации и действия выбора первого склада для изменения остатков.
- Старые привязки локаций в форме склада и магазина, переключатель возврата
  профиля на прежние тарифы, переключатели отключения складского учёта
  и выбора первого склада.
- Региональные переопределения сроков доставки в формах товара и предложения.
  Сроки выдаются из подготовки источника и перевозки по профилю склада.

Таблицы и исторические связи не уничтожаются: они нужны для сохранности
старых заказов и последующего контролируемого архивирования. Их наличие
не включает старый расчёт. Старые ресурсы не имеют страниц и запрещают доступ,
а не просто скрывают пункт навигации.

Региональные правила **цены товара**, видимости каталога и оплаты — отдельные
механизмы. Их исторические идентификаторы не превращаются в покрытие склада
и не восстанавливают расчёт доставки по локации. Этот переход не является
удалением существующих персональных/региональных цен.

## Новый API

### Адреса

Использовать `/api/v1/address-directory/*` и `/api/v1/localities/*`.
Значение `directory_external_id` — идентификатор справочника, а не ID
из старой таблицы `shipping_locations`.

### Доставка: POST /api/v1/shipping/quote

`directory_external_id` здания или `address_id` сохранённого адреса текущего
покупателя. Можно передать `items` для предварительного расчёта, иначе берётся
корзина. Для предварительного расчёта допускается территория; оформление
доставки требует здание.

Услуги выбираются по `selected.service_options`, а цены, сроки, покрытие и
остатки проверяются сервером. Клиент не передаёт стоимость услуги.
Отсутствие подходящего профиля/остатков — недоступная доставка, не бесплатная.

### Самовывоз: POST /api/v1/shipping/pickup-options

Адрес доставки не нужен. Можно передать:

```json
{"items":[{"product_id":123,"quantity":2}]}
```

Иначе проверяется текущая корзина. Ответ `pickup` содержит `warehouse_id`,
`store_id` (либо null для выдачи непосредственно со склада), адрес,
часы работы, календарную готовность и остатки по запрошенным SKU.
Пустая корзина — 422, отсутствие подходящих точек — пустой список.

Одна точка должна обеспечить всю корзину. Остатки разных складов не
складываются для разрешения конкретного заказа.

### Оформление: POST /api/v1/orders

Контакты, оплата и согласия остаются прежними.

- `delivery_type=delivery`: здание `directory_external_id` или принадлежащий
  покупателю `address_id`. `warehouse_id` необязателен: если указан, должен
  быть среди подходящих источников. Услуги — только из профиля этого источника.
- `delivery_type=pickup`: обязателен `warehouse_id`, `store_id` задаётся для
  магазина. Адрес покупателя не подменяет адрес точки выдачи. Сборка,
  подъём и дополнительные услуги доставки для самовывоза не рассчитываются.
- `shipping_location_id`, `shipping_method_id`, сырой `address`, `delivery_cost`,
  `assembly_cost`, `additional_services.*.price` запрещены: ответ 422.

Оформление всегда пересчитывает условия; результат предварительного расчёта
не является доверенным тарифом. Заказ фиксирует источник и условия в
`fulfillment_snapshot`; резерв и возврат выполняются для этого же источника.
Клиент не передаёт snapshot, fingerprints или состояние резерва.

## Магазин, площадка и склад

- Магазин — публичная страница и точка выдачи, не второй учёт остатков.
- Для магазина с остатками выбирается существующий активный физический
  склад с количественным учётом и та же общая площадка `PhysicalSite`.
- Общая площадка обязательна в форме магазина. Её адрес — общий источник
  адреса магазина и связанного склада; отдельная точка погрузки склада
  может иметь собственные координаты.
- Готовность самовывоза едина для списка магазинов, списка точек и резерва:
  действующий физический склад, количественный учёт, непустой адрес,
  включённая выдача, согласованная площадка магазина и склада.
- Удаление/изменение магазина между выбором и резервом требует нового
  расчёта. Подмена пропавшего магазина выдачей со склада запрещена.
- Смена города/отключение магазина инвалидирует и фильтрованные списки,
  и список городов, включая драйверы кэша без тегов.

## Профили и услуги

Доставка применяется только по `directory_territories`, радиусу или их
пересечению. Старые pivot-связи с локациями не используются для наличия,
расстояния, расчёта доставки и сроков.

Типы обработки и дополнительные услуги остаются справочниками. Цены задаются
в `service_tariffs` конкретного профиля. Глобальная базовая цена услуги
не участвует в расчёте и больше не предлагается для редактирования.
Автоматический расчёт поддерживает фиксированные тарифы, не цены «от» и
не договорные цены.

Для нового профиля `service_tariffs=[]` означает явно отсутствие услуг.
Историческое `service_tariffs=null` **не** означает бесплатный тариф:
профиль не участвует в покрытии/расчёте, пока оператор не сохранит новые
тарифы. Автоматически переносить стоимость из старой локации запрещено.

Складской учёт обязателен. Старые значения переключателей в БД не возвращают
учёт по общему `product.stock`. Предзаказ требует подтверждённой записи
доступности у активного источника, а не только `product.backorder=true`.

## Заказы в админке и история

Сохранённые условия заказа нельзя изменять обычным обновлением формы:
иначе можно обойти пересчёт, банковскую сумму и резерв. Старая форма
ручного создания заказа по локации отключена; создание — через складской
checkout API. Для другого адреса/источника/состава/услуг нужно переоформление
через полноценный расчёт. Статусы, контакты и комментарий редактируются.

Исторические заказы без `fulfillment_snapshot` не списывают и не возвращают
остатки на первый склад при изменении статуса. Источник этих операций нельзя
восстановить догадкой; исторические корректировки согласовываются отдельно.

## Перед запуском на сервере

1. Резервная копия БД и текущего релиза; выпуск строго через репозиторий.
2. Обновить backend и autoload, очистить старый route/view/config cache,
   перезапустить очереди штатным способом. Новых миграций эта доработка
   не требует; старые таблицы не удаляются.
3. Настроить реальные адреса/площадки, связанные магазины и профили.
   Не придумывать тарифы и адреса. По аудиту production было два склада,
   ноль магазинов, ноль площадок, ноль профилей; у второго склада нет
   адресного идентификатора и координат.
4. Проверить `shipping:audit-service-tariffs`: null-тарифы требуют настройки.
5. Прогнать доставку и самовывоз: конкретный SKU, услуги, заказ, резерв,
   отмена и однократный возврат. Проверить исторические заказы отдельно.
6. Старые запросы клиента после обновления получат 404/422. Фронтенд
   должен использовать описанный контракт; обратной совместимости нет.

Наличие новых обработчиков не означает, что production уже имеет реальные
настроенные тарифы. Без профилей новая доставка закономерно недоступна.
