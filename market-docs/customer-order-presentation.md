# Кабинет: обзор, компактный список и отображение заказа

Все URL относительно `/api/v1`, нужна авторизация покупателя. Чтение не меняет статусы,
остатки, платежи и не запускает банковские запросы.

## Обзор

`GET /orders/summary` возвращает `{total, active, completed, cancelled, last_order}`.
Считаются только заказы с user_id текущего покупателя. Последний — по created_at DESC,
id DESC; при отсутствии заказов last_order=null, счётчики=0.
Группы: completed=delivered, cancelled=cancelled, остальные (включая неизвестные будущие)
active. Возврат денег и оплата не меняют группу выполнения заказа.
Счётчики считаются агрегацией без загрузки состава всех заказов.

## Список

`GET /orders?view=compact&page=1&per_page=10&group=active`.
Параметры page/per_page/group также включают компактный режим без view.
per_page: 1–50, по умолчанию 10; group: active/completed/cancelled, необязателен.
Необязательный status фильтрует внутренний код дополнительно к группе.
Сортировка created_at DESC, id DESC. Ответ: `{data, links, meta}` с current_page,
last_page, per_page, total. Некорректные параметры — 422, нет входа — 401.

Карточка списка и last_order содержат id, number, status, status_label, total,
delivery_type, created_at, items_count (число строк состава), presentation.
Контакты, адрес, состав, комментарии и полная история в компактную карточку не входят.
Сведения для отображения подгружаются пакетно: нет отдельных запросов на каждую карточку.

Старый `GET /orders` без новых параметров сохраняет прежний полный массив data.
Деталь `GET /orders/{id}` сохраняет `{order: ...}` и существующие поля. В неё добавлены
presentation и paid_at. Приватные ссылки гостевых заказов продолжают работать отдельно.
Фронт может перейти на новые методы без одновременного изменения старых клиентов.

В TypeScript добавлены api.orders.summary(), api.orders.listCompact(params),
CustomerOrderCard, OrderSummary, CustomerOrderPresentation. Существующие страницы пока
используют прежний метод list(): переход UI на новые методы выполняется отдельно.

## Представление

```json
{
  "version": 1,
  "group": "active",
  "status": {"code": "in_transit", "label": "Заказ в пути"},
  "payment": {
    "status": "paid", "label": "Оплачен", "paid_at": null,
    "amount_paid": 10000, "amount_refunded": 0,
    "refund_status": "none", "refund_label": null
  },
  "progress": [
    {"code": "created", "label": "Создан", "state": "completed", "occurred_at": "2026-11-19T10:00:00.000000Z"},
    {"code": "preparing", "label": "Подготовка", "state": "completed", "occurred_at": null},
    {"code": "shipping", "label": "Отправлен", "state": "current", "occurred_at": null},
    {"code": "received", "label": "Доставлен", "state": "pending", "occurred_at": null}
  ],
  "message": "Заказ в пути"
}
```

Фронт отображает полученные label, message и упорядоченный progress, не строит цепочку
по внутреннему OrderStatus. code может расширяться. state: completed/current/pending,
для отмены также skipped/cancelled. version — версия структуры, а не набора статусов.
Все даты ISO 8601 UTC; локальное время отображает фронт. Дата этапа — первое реальное
событие этого этапа в истории. Прошедший этап может не иметь даты: она тогда null.
Создание берётся из created_at, остальные даты не заменяются датой заказа/updated_at.

Оплата отдельна от исполнения. Статусы payment: unpaid, pay_on_receipt, partially_paid,
paid, partially_refunded, refunded. Наличные до оплаты — «Оплата при получении»,
отменённый неоплаченный заказ — «Не оплачен». amount_paid берётся из подтверждённых
сумм платежей, amount_refunded — только из завершённых payment_refunds.
paid_at определяется по событиям paid в payment_history: момент достижения полной суммы.
При неполной оплате или недостатке исторических данных paid_at=null. Поле не вычисляется
по updated_at платежа, дате заказа или его логистическому статусу.
refund_status: none/pending/manual_review/completed; refund_label готов для отображения.
Отмена сама по себе не означает возврат. В процессе возврата сохраняется факт оплаты,
отдельно показывается refund_label. Старое payment_status=paid/unpaid оставлено без изменения;
новый интерфейс должен использовать presentation.payment.

Для доставки этапы: Создан → Подготовка → Отправлен → Доставлен.
Для самовывоза: Создан → Подготовка → Готов к выдаче → Получен.
assembled отмечает только подготовку; готовность выдачи требует отдельного явного статуса.
ready_for_pickup зарезервирован в отображении, но не добавляет действие перехода в движок.
При отмене выполненные этапы сохраняются, последующие skipped, добавляется отмена
с фактической датой из истории. Текущего этапа после отмены нет.

## Подключение будущей логистики

`config/customer_orders.php` определяет группы, подписи, сопоставления и цепочки этапов.
Неизвестный статус остаётся active с нейтральной подписью и последним известным этапом.
Модуль логистики может дополнять конфигурацию или заменить CustomerOrderPresentation
через контейнер, не меняя клиентский контракт. Транспортные события и разделение заказа
на несколько отправлений этим изменением не реализованы.

Новых миграций нет. При установке очистить кэш маршрутов и конфигурации.
В develop/Beget изменения попадают только после отдельного слияния и выкладки.
