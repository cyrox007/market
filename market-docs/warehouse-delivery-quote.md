# Расчёт доставки по адресу и покрытию склада

Локальная реализация, без изменений React и без выкладки на сервер.

## Настройка в админке

Склад → «Доставка» → «Добавить профиль доставки»:

1. Название направления.
2. Покрытие: выбранные территории, радиус или территории **и** радиус одновременно.
3. Добавьте территории последовательно: регион → населённый пункт (необязательно). Пустой населённый пункт означает весь регион. Дочерние адреса наследуют покрытие. Можно добавить несколько территорий.
4. Стоимость и срок доставки от–до в календарных днях.
5. При необходимости доплата за километр и бесплатная доставка от суммы товаров.

Меньшее число приоритета означает более высокий приоритет. Среди подходящих профилей одного склада используется первый по приоритету, затем ID. Специальный городской тариф должен иметь приоритет выше областного. Старые привязки «Локаций» оставлены в свёрнутом разделе только для старого расчёта; автоматически сопоставлять их по названиям небезопасно.

Идентификаторы и иерархия территорий проверяются на сервере по адресному API. Совместимость ГАР/КЛАДР основана на ID и кодах одного уровня, не на похожести названий.

## Запрос расчёта

`POST /api/v1/shipping/quote` с cookie текущей корзины:

```json
{"directory_external_id":"GUID здания ГАР"}
```

Вместо идентификатора здания авторизованный пользователь может передать `address_id` своего адреса профиля. Необязательный `region_id` используется существующими региональными правилами цены товара. Товары, количества и цены берутся сервером из корзины, `order_amount` и клиентские суммы не принимаются.

Для отдельного дома из групповой записи КЛАДР используется `код::номер` (номер URL-кодирован). Сервер проверяет принадлежность номера записи; диапазоны не принимаются. Для здания ГАР суффикс номера запрещён.

Ответ: `available`, `currency`, `subtotal`, проверенный `address`, список `options` и выбранный `selected`. В варианте: `warehouse_id`, `profile_id`, `delivery_cost`, `transit_days_min/max`, `processing_days_min/max`, итоговые `delivery_days_min/max`, `distance_km`, `distance_type`. Общий срок = максимальная подготовка товаров на складе + срок доставки профиля. Стоимость = базовая цена + километры × доплата; при достижении порога бесплатной доставки — 0.

Выбирается самый дешёвый подходящий склад, затем минимальный верхний срок и ID для стабильности. Один склад должен обеспечить **всю корзину** в нужном количестве. Для фабрик проверяется `available_to_order`, учитываются сроки подготовки каждой позиции. Разделения заказа между складами нет: если общей точки отгрузки нет, возвращается недоступность, а не выдуманная сумма.

422 + `available:false`: нет подходящего покрытия/остатков либо необходимых координат. 503: справочник недоступен — это не отсутствие покрытия. Невалидный адрес/пустая корзина — 422 с ошибками полей.

## Создание заказа

`POST /api/v1/orders`: обычные контактные поля и способ оплаты, `delivery_type:delivery`, `directory_external_id` **или** `address_id`. Для нового адреса дополнительные детали передаются отдельно:

```json
{
  "contact_name":"Покупатель",
  "contact_phone":"+79991234567",
  "contact_email":"buyer@example.ru",
  "payment_method":"card",
  "delivery_type":"delivery",
  "directory_external_id":"GUID здания ГАР",
  "delivery_details":{"apartment":"12","room":null,"entrance":"1"}
}
```

`shipping_location_id` для нового пути не нужен. Сумма пересчитывается заново; клиентский `delivery_cost` игнорируется. В `order.fulfillment` сохраняются склад, профиль, товары, цена и сроки расчёта. Цена и диапазон общего срока сохраняются также в полях заказа. Новый проверенный адрес сохраняется в профиле. Чужой `address_id` недоступен.

В транзакции проверяются актуальность тарифа и доступность выбранного склада; физический остаток блокируется и уменьшается именно там. При отмене возвращается в тот же склад однократно. Старый обработчик не списывает такой заказ второй раз. При недостаточном остатке/изменившемся тарифе создание отклоняется, изменения транзакции откатываются.

## Ограничения пилота

- Расстояние **по прямой**, не автомобильный маршрут. Это явно указано в админке и `distance_type`.
- Центр населённого пункта не подменяет координаты здания. Фиксированные территориальные тарифы работают без координат; радиус/километровые — нет.
- Координаты зданий пока имеют пилотное покрытие. Заполнение ГАР не гарантирует координаты каждого дома.
- Выбор покрытия сейчас последовательный регион → населённый пункт, не многоуровневый визуальный tree-widget с районами.
- Подъём, сборка и дополнительные услуги не включены в новый тариф склада. Запрос этих услуг отклоняется с явной ошибкой, чтобы не показать ложную итоговую сумму. Старый путь расчёта их сохраняет.
- Произвольные `constraints` профиля не интерпретируются: такие профили исключаются из нового расчёта.
- React пока не вызывает новый расчёт. Фронтендеру нужно подключить `/shipping/quote` и передавать выбранный адрес при создании заказа. Старые клиенты без идентификатора справочника продолжают использовать прежний расчёт по локациям.
