# Журнал действий пользователей

Первая итерация. Отдельная подсистема, не заменяет банковские журналы, историю заказа и технические логи.

## Включение

1. Выполнить миграции.
2. Установить `ACTIVITY_AUDIT_ENABLED=true`, обновить config cache.
3. В панели admin_sv открыть «Аудит и безопасность → Журнал действий». Доступ super_admin или роль admin с явным правом viewAny activity_audit. Экспорт требует отдельного export activity_audit. Менеджер, редактор и покупатель не получают доступ даже при ошибочно выданном разрешении. Просмотр страницы фиксируется.
4. `ACTIVITY_AUDIT_BEHAVIOR=true` задаёт начальное значение сбора событий серверных запросов каталога; сохранённые настройки панели имеют приоритет и; это не запись кликов и не session replay. По умолчанию выключено.
5. Проверить cron: `audit:prune-activity` ежечасно удаляет просроченные строки ограниченными пачками.

## Формат и ограничения

UUID события/запроса, псевдоним сессии (HMAC от отдельного случайного nonce, не session ID), инициатор, источник (витрина, админка, интеграция, callback банка, система), объект, результат, разрешённые детали. ID пользователя/объекта сохраняются без внешнего ключа, чтобы удаление аккаунта не уничтожало историю автоматически. Сроки: безопасность/админ/заказы 365 дней, аккаунт/покупки 90, каталог 30. Согласовать с политикой персональных данных до включения.

Запись успешных изменений через наблюдатели участвует в транзакции вызывающего кода, если таковая есть. HTTP-события фиксируют исход ответа после обработки запроса, best effort; они не являются доказательством фактической оплаты и могут отсутствовать при аварии процесса. Не все массовые операции через query builder/pivot охвачены. Не сохраняются пароли, токены, cookie, IP, контактные значения, произвольные payload, строки поиска, сырые URL и тексты исключений. Записываются только разрешённые имена изменённых полей и ограниченные числовые/логические значения.

Доступ к журналу закрыт, интерфейс не предоставляет действий изменения и удаления; очистка по расписанию выполняется напрямую. Это не WORM-хранилище: привилегированный оператор БД может менять записи. Фильтры по дате, субъекту, пользователю, заказу, категории, результату; поиск по сессии/запросу. Ссылки на отфильтрованный журнал из карточек пользователя и заказа.

## Дальнейшее расширение

Отдельный визуальный таймлайн, полное покрытие интеграционных событий и перенос источника в фоновые задачи, транзакционный outbox для критических записей вне транзакций, дополнительные события фронтенда, нагрузочная приёмка и проверка отказа БД. Не включать поведенческий сбор без согласования цели и политики данных.

## Управление и экспорт

Настройки аудита доступны только super_admin. Для критических категорий срок 90–1095 дней, остальных 7–1095; изменение фиксируется вместе с записью настроек. Выгрузка CSV текущей выборки максимум 5000 строк, требует отдельного права и записи audit.export перед выдачей. История аккаунта включает предшествующие гостевые события только при успешной авторизации в однозначно связанной сессии; при нескольких аккаунтах гостевые записи не присоединяются. CSV содержит псевдонимы и идентификаторы; хранить как персональные данные.

Поведенческие события выполняются в отдельной очереди `activity-audit` (отдельный короткий cron-воркер). UUID сохраняется между попытками, время события не зависит от задержки очереди. Неудачная постановка не блокирует витрину. Сводка за 24 часа и график за 7 дней доступны только в журнале; кэш 60 секунд.
