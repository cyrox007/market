# Адреса, склады и заказы — инструкция фронтенду

Контракт подготовки к запуску, 20.10.2026. Код и наличие данных проверяются отдельно от факта деплоя.
Публичный адресный API и сайт — разные приложения. Дома ещё переносятся; координаты имеют неполное покрытие.

## 1. Готовность и выбор местоположения

Фронт обращается к backend сайта, не к БД и не к внешним геокодерам:

- `GET /api/v1/address-directory/status` → `data.settlementsReady`, `data.availableLevels.{regions,localities,streets,buildings}`, `data.nationwideReady`.
- `GET /api/v1/address-directory/regions` → `data[]`.
- `GET /api/v1/address-directory/localities?parentExternalId=<GUID региона>&q=Лип&limit=50`.
- `GET /api/v1/address-directory/streets?parentExternalId=<GUID населённого пункта>&q=Мос`.
- `GET /api/v1/address-directory/buildings?parentExternalId=<GUID улицы или населённого пункта>&q=10`.
- `GET /api/v1/address-directory/hierarchy/<GUID>` → `data.target`, `data.path[]`, `data.label`.

`settlementsReady` означает покрытие страны населёнными пунктами, НЕ готовность домов или геолокации.
`availableLevels` — подтверждённое полное покрытие соответствующего уровня; до завершения переноса нижние уровни могут быть частичными.
`nationwideReady` — завершённый и проверенный полный справочник, не просто количество регионов.

В элементах: `externalId` — канонический GUID ГАР; `objectId` — числовой ID ГАР **строкой**; `kladrCode` — код совместимости либо null.
Все коды сохраняются строками. Нельзя заменять GUID названием, обрезать/дополнять КЛАДР нулями или передавать его как ID бизнес-локации.
Федеральный город может иметь один GUID в роли региона и населённого пункта. Город на административном уровне также остаётся тем же объектом ГАР; дубликат не создаётся.

## 2. Геолокация и каталог

Канонические маршруты выбора города уже описаны в `frontend-fulfillment-contract.md`; они используют тот же справочник.
Координаты могут быть null. Центр города обозначается `coordinatePrecision=settlement_centre`, он не становится точкой склада или здания.
Подтверждение найденного ближайшего города остаётся за пользователем. При неизвестных координатах не показывать нулевое расстояние и не обещать доставку по радиусу.
`directory_external_id` задаёт объект ГАР, `region_id` — отдельную бизнес-локацию региональных цен; это разные идентификаторы.
Фильтры и сортировку расстояния используй по существующему контракту каталога; локальная сортировка одной страницы некорректна.

## 3. Расчёт и оформление доставки

`POST /api/v1/shipping/quote` — `directory_external_id` и текущая корзина либо `items` для предварительного расчёта карточки.
Для окончательного заказа требуется конкретное здание, не центр города:

```json
{
  "contact_name": "Покупатель",
  "contact_phone": "+79991234567",
  "contact_email": "buyer@example.ru",
  "payment_method": "card",
  "delivery_type": "delivery",
  "directory_external_id": "GUID здания из ответа API",
  "delivery_details": {"apartment": "12", "entrance": "1", "room": null}
}
```

Создание — `POST /api/v1/orders`; сохранённый собственный `address_id` допустим вместо GUID. При передаче обоих они обязаны совпадать.
Фронт НЕ присылает `gar_guid`, КЛАДР, родительские коды и снимок: backend заново разрешает адрес и пересчитывает тариф/остаток.
Квартира/подъезд/комната — отдельные детали, не часть идентификатора здания.

## 4. Самовывоз

Выбирай вариант `pickup[]` из расчёта. При заказе передавай `delivery_type=pickup`, `warehouse_id` и `store_id`, если он задан выбранным вариантом.
Не подменяй адрес точки самовывоза домашним адресом покупателя.
Backend определяет адрес из площадки/склада; цена самовывоза — 0, остаток повторно проверяется на выбранном складе.

Вариант самовывоза получает `warehouse_external_id` и `address_directory` — снимок адреса точки либо null, если она ещё не настроена.
Не выдумывать коды при null. Такие склады требуют настройки адреса оператором до запуска.

## 5. Ответ заказа и интеграция

`order.address_directory` — неизменяемый снимок на момент оформления (или null для исторического/не настроенного адреса):

```text
version, external_id, gar_guid, object_id, kladr_code, source, label,
path[{externalId, objectId, kind, name, type, kladrCode, ...}],
details{apartment, room, entrance, floor, intercom, comment},
latitude, longitude, coordinate_source, coordinate_precision
```

`order.fulfillment.address_directory` содержит тот же снимок. Правка адреса профиля или склада не должна менять старый заказ.
Для доставки это адрес покупателя; для самовывоза — выбранной точки, не профиля пользователя.
Обмен с API/1С передаёт `addressExternalId`, `addressDetails`, `warehouseExternalId` и совместимую строку `address`.
`warehouseExternalId` — код склада, не `storeExternalId` старого справочника магазинов; эти коды не подменяются друг другом.
Принимающий API проверяет GUID по ГАР и формирует собственный снимок с кодами всей иерархии.
Выкладывать принимающий DTO/хранилище перед включением отправки новых полей сайта; иначе строгая валидация старого API вернёт 400.

## 6. Ошибки и приёмка

- 503 — справочник недоступен; не заменять пустой выдачей и не очищать выбранный адрес.
- 422 — невалидный выбор/нет подходящей доставки; показывать ошибку поля или расчёта.
- Пустой список при частичном покрытии домов не означает, что дома не существует.
- При смене города сбрасывать улицу/дом; при смене здания — прежний расчёт. Новый расчёт обязателен.

Перед запуском проверить: Москва/СПб как города; обычный город; одноимённые сёла; дом без улицы; корпус/строение; адрес без координат;
доставка и самовывоз с одного и разных складов; чужой address_id; изменение адреса после оформления;
создание заказа → API/1С → чтение заказа со всеми кодами и деталями. Результат полного интеграционного прогона фиксировать отдельно от unit-тестов.
