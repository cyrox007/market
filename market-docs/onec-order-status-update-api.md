# Обновление статуса заказа из 1С — входящий API

**Первый этап. По умолчанию выключен; не развёртывать без проверки.**

## Контракт

**POST** `/api/v1/integration/1c/orders/{orderId}/status`

HTTPS на production; заголовок `X-1C-Orders-Token`. Отдельный токен с единственным правом `orders:status:write` выдаётся через административную панель «Интеграции → Доступ 1С к заказам». Токены чтения `orders:read`, статический `ONEC_ORDERS_READ_TOKEN`, клиентская сессия и `ONEC_API_KEY` не дают права записи.

Активация: `ONEC_ORDER_STATUS_WRITE_ENABLED=false` по умолчанию. Лимит: `ONEC_ORDER_STATUS_WRITE_PER_MINUTE=20` запросов в минуту/IP. `orderId` — внутренний ID из GET 1С.

~~~json
{
  "event_id": "7b7cce9f-920b-42f7-9524-72a823b7f56c",
  "expected_status": "assembling",
  "status": "assembled",
  "comment": "Собран на складе"
}
~~~

`event_id` — UUID бизнес-события 1С, **не менять при повторной доставке**. `expected_status` защищает от устаревших обновлений. Комментарий необязателен (до 500 символов).

HTTP 200:

~~~json
{
  "data": {
    "event_id": "7b7cce9f-920b-42f7-9524-72a823b7f56c",
    "order_id": 123,
    "number": "ORD20261123000001",
    "previous_status": "assembling",
    "applied_status": "assembled",
    "current_status": "assembled",
    "duplicate": false
  }
}
~~~

Повтор точно того же события → HTTP 200, `duplicate=true` (без повторного выполнения побочных эффектов). При этом `current_status` может отличаться от `applied_status`, если заказ уже продвинулся дальше. Повтор того же UUID с другими данными → HTTP 409.

## Переходы

Используется текущий `OperatorOrder::next()`:

- `assembling` или `accepted` → `assembled`;
- `assembled` → `delivered` при самовывозе, иначе → `shipped`;
- `shipped` → `in_transit`;
- `in_transit` → `delivered`.

Обязательны завершённый `cooling_until` и действующие проверки оплаты. Нельзя менять отменённый заказ, пропускать шаги, произвольно корректировать суммы, оплату и резервы. Для прочих сценариев требуется оператор.

Коды: **401** токен или право; **403** отключено/HTTPS; **404** заказ не найден; **409** конфликт состояния/бизнес-правил/повтор чужого UUID; **422** неверный JSON; **429** лимит запросов. Ответы не кэшируются.

История и складские/почтовые события используют обычный `Order::changeStatus()`. Исходящая синхронизация *того же* статуса с 1С подавляется, чтобы избежать цикла. В таблице `onec_order_status_update_events` сохраняются номер события, хеш данных, переход, токен, IP и дата.

## Приёмка

1. Выполнить миграцию и PHPUnit тесты; проверить CI.
2. Согласовать с разработчиком 1С отображение их статусов на допустимые значения.
3. Выдать **отдельный токен записи**, установить IP/срок и включить флаг только после тестов.
4. Проверить успешное обновление, повтор, попытку пропуска, период ожидания, неоплату и отзыв токена.

На данном этапе отсутствуют команды 1С для отмены, оплаты, изменения остатков и обещаний доставки, а также отдельный поток изменений с гарантированной доставкой и ACK.
