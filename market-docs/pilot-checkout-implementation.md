# Пилот заказов: контракт и ввод в работу

## Состояние

Реализация подготовлена в ветке `fix/pilot-order-audit`. Это локальные изменения; production ими не обновлён. Исходные аудиты от 26 октября описывают состояние **до** этой реализации.

## Заказ и время

`POST /api/v1/orders` создаёт заказ в `manager_processing` («В обработке у менеджера») с `cooling_until = created_at + 60 минут`. Оплата не меняет дедлайн. До него покупатель может отменить и оплаченный заказ. Ровно на дедлайне прямая отмена запрещена независимо от состояния очереди.

Планировщик каждую минуту выполняет `orders:advance-cooling`: оплаченный или с оплатой при получении переводится в `assembling`, неоплаченный заказ онлайн-эквайринга — в `cancelled`. До окончания охлаждения dispatch и само задание отправки в 1С блокируют передачу. Смена статуса выполняется под блокировкой заказа в транзакции.

`POST /api/v1/orders/one-click` подготавливает прямое оформление с `items`; возвращает цену и `submit_endpoint`. Заказ создаёт последующий POST `/orders` с адресом/самовывозом и контактами. Корзина при прямом оформлении сохраняется.

## Повторы и доступ

При создании обязателен `Idempotency-Key` длиной 16–128 символов. Один ключ + одна сессия + одинаковое тело возвращают тот же заказ с `Idempotency-Replayed: true`. Другое тело с тем же ключом — 409. Ответ хранится зашифрованным. Нельзя повторять оформление с новым ключом только из-за сетевого таймаута. Минимальная правка клиента повторно использует ключ пять минут для одинакового тела.

Ответ создания содержит `guest_order_token`. Его следует хранить как секрет и передавать заголовком `X-Order-Token`, не в URL. Доступ на 30 дней:

| Запрос | Назначение |
|---|---|
| GET `/api/v1/order-access/{id}` | Заказ гостя или авторизованного владельца |
| POST `/api/v1/order-access/{id}/cancel` | Прямая отмена до дедлайна; необязательный `reason` |
| POST `/api/v1/order-access/{id}/cancellation-request` | После дедлайна: `reason`, 3–1000 символов; повтор не создаёт вторую заявку |
| GET `/api/v1/orders/{id}/payment-config` | Конфигурация оплаты для владельца, сессии создателя или гостевого токена |

Ресурс заказа возвращает `status`, `status_label`, `cooling_until`, `server_time`, `payment_status`, `can_be_cancelled`, `can_request_cancellation`, `can_pay`, `integration_state`, `cancellation_request`, `refund_task`. Кнопки должны опираться на возможности сервера. Полученный guest token не заменяет авторизацию ко всем заказам покупателя.

Заявки после дедлайна рассматривает менеджер в «Заявки на отмену». Рассмотрение заявки само по себе не отменяет заказ. Права изменения — права изменения заказа.

## Резервы и остатки

Добавление в корзину резервирует конечный остаток одного склада на 30 минут. Повторное изменение до истечения не продлевает исходный срок. После истечения резерв можно получить заново, если остаток свободен. Другим покупателям резерв недоступен; своя корзина продолжает видеть свою доступную единицу. Резерв привязан к сессии; это не защита от злоупотреблений через множество независимых сессий.

Оформление атомарно переносит резерв в `product_warehouse_stocks.reserved_quantity`. `quantity` — физический остаток, из доступности вычитаются резервы заказов и активные резервы чужих корзин. Отмена освобождает резерв один раз; доставка списывает физический остаток и резерв. Для старых заказов сохранена версия прежнего механизма списания. Снимки импорта 1С не стирают `reserved_quantity`.

Стоимость берётся из выбранного складского профиля: доставка, подъём, сборка и выбранные услуги. В заказе фиксируется снимок. В 1С передаются текст адреса, GAR GUID, КЛАДР при его наличии, доступные коды иерархии; при самовывозе — флаг и код склада. Отсутствующий код дома нельзя выдумывать из кода улицы: принимающая сторона должна поддержать неполный КЛАДР + текст/GAR или согласовать отклонение адреса.

## Оплата и возвраты

Банковские callback проверяются шлюзами; обновление результата блокирует заказ и платёж. Повтор уже успешной оплаты не проводит её второй раз. Поздняя оплата отменённого заказа не возобновляет заказ и создаёт задачу возврата.

«Возвраты после отмены» показывает оплаченные отменённые заказы и остаток к возврату. Это очередь **ручной проверки**, не обещание автоматического возврата. Для поддерживаемого Raiffeisen E-commerce возврат запускается существующей кнопкой заказа; задача пересчитывается по зарегистрированным возвратам. Для другого эквайринга необходима операция через банк и подтверждённая сверка; одного изменения статуса задачи для возврата денег нет.

## Закрытые цены Авито

Суперадминистратор создаёт запись в «Цены по закрытым ссылкам»: конкретный товар/SKU, цена, начало и конец действия. Токен из 32 случайных байт выдаётся в уведомлении один раз, в БД хранится SHA-256. Повторный выпуск отзывает прежнюю ссылку и её доступ. Ссылку можно пересылать — это согласованный сценарий.

Переход `/offer/{token}` активирует серверную сессию и переводит на обычную карточку без секрета в URL. API-альтернатива — POST `/api/v1/private-offers/activate` с `{token}`, GET `/api/v1/private-offers/current` для активных предложений. Доступ не зависит от цены, присланной браузером. Ссылка задаёт максимальную цену: если обычная цена ещё ниже, покупатель получает меньшую.

Для персонализированных публичных запросов товаров нужен `X-Private-Price-Context: 1`. Cookie `has_private_offer=1` — открытая подсказка обхода общего SSR-кеша, **не право на скидку**. Право проверяется по сессии, активности, срокам и хешу. Фронт автоматически передаёт заголовок и не использует общий SSR-кеш. Обычные посетители видят обычную цену; публичное ценовое правило не создаётся. Минимальные изменения клиента не меняют оформление страниц.

`expected_subtotal` при POST `/orders` фиксирует сумму товаров, которую подтвердил покупатель. Несовпадение — 409. Если сохранённый доступ истёк/отозван, оформление без новой подтверждённой суммы тоже возвращает 409. Уже созданный заказ сохраняет цену снимка.

## Ввод в работу

1. Согласовать изменения в репозитории, сделать резервную копию и применить миграцию `2026_10_26_160000_add_pilot_order_lifecycle.php` перед включением нового кода.
2. Убедиться в работе Laravel scheduler каждую минуту. Запустить worker `integration-orders` отдельно от старой массовой очереди `integration-1c`, перезапустить workers после обновления. Сам backlog не удалять.
3. Задать URL принимающего API, ключ и рабочие настройки оплаты. Очередь отправляет только после охлаждения; ошибки видимы как `integration_state=failed`. Поддержка Idempotency-Key/дедупликации на принимающей стороне обязательна для защиты от повторного приёма при таймауте. Строго однократная доставка этим кодом не гарантируется.
4. Настроить действующий магазин, центральный склад, адрес, покрытие и реальные тарифы; самовывоз включать только для готовой точки. На прочитанном production в момент аудита профили доставки и магазины отсутствовали — тестовые фикстуры не заменяют настройку.
5. Обновить клиент и SSR вместе с API: старый клиент без Idempotency-Key получит 422. Сохранение гостевого токена и отображение новых статусов необходимо подключить потребителю API. Новый API не означает, что старый интерфейс уже умеет показать все новые действия.
6. Перед открытием оплаты провести согласованный банковский тест и конкурентный тест последней единицы на MySQL. Локальные автоматические тесты используют SQLite и поддельные внешние ответы, реальные банковские списания и отправка production-заказов не выполнялись.

Миграция добавляет резервную колонку к таблице остатков: на большой production-таблице заранее оценить DDL/metadata lock. Не запускать откат миграции при активных резервах/заказах без их сверки.
