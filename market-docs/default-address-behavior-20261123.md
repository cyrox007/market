# Основной адрес пользователя: единые правила API (23.11.2026)

## Зачем изменили

Ранее `POST /api/v1/addresses` всегда создавал запись с `is_default=false`.
Сохранение адреса и назначение основным требовали двух HTTP-запросов,
а после удаления основного адреса оставшиеся адреса могли не иметь основного.
Это затрудняло редактор адресов и создавало неопределённое состояние.

## Правила

| Операция | Поведение |
| --- | --- |
| Первый адрес | Автоматически становится основным, даже при `is_default=false` или отсутствии поля |
| Создание второго адреса без флага или с `is_default=false` | Текущий основной сохраняется |
| Создание с `is_default=true` | Новый адрес становится основным в **одном** `POST` |
| Обновление с `is_default=true` | Редактирование и перенос флага выполняются в **одном** `PUT` |
| Обновление без флага | Существующий основной не меняется |
| Обновление с `is_default=false` для второстепенного | Допустимо, ничего не переключает |
| Обновление с `is_default=false` для текущего основного | HTTP 422, ошибка поля `is_default`: сначала выбрать другой |
| Удаление основного | Основным становится самый ранний оставшийся адрес: `created_at ASC, id ASC` |
| Удаление другого адреса | Основной остаётся прежним |
| Удаление последнего адреса | Основного больше нет, `default_address_id: null` |
| Старые записи без основного | При следующей операции записи через API адресов выбирается самый ранний |
| Несколько основных в старых данных | При следующей операции записи через API адресов остаётся один — самый ранний из отмеченных |

Установка основного адреса через `POST /api/v1/addresses/{id}/set-default`
продолжает работать для существующих клиентов.

## Контракт для фронтенда

```http
POST /api/v1/addresses
Content-Type: application/json

{"directory_external_id":"building-123","title":"Дом","is_default":true}
```

Ответ `201` уже содержит фактическое `address.is_default: true`.
При `PUT /api/v1/addresses/{id}` можно передать `is_default: true`
вместе с изменяемыми полями. Если checkbox текущего основного адреса снят,
сервер возвращает `422` с `errors.is_default`: UI следует предлагать
выбрать другой адрес, а не оставлять аккаунт без основного.

`DELETE /api/v1/addresses/{id}` и старый
`POST /api/v1/addresses/{id}/set-default` дополнительно возвращают
`default_address_id`, не изменяя прежние `message` и HTTP-коды.
После удаления можно обновить локальное состояние списка адресов
из ответа или вызвать `GET /api/v1/addresses`.

Пример ответа на удаление:

```json
{"message":"Адрес успешно удален","default_address_id":42}
```

## Целостность, безопасность, ограничения

- Операции с основным адресом объединены в транзакции `DefaultAddressManager::forUser`.
- Строка владельца из `users` блокируется `lockForUpdate` до окончания транзакции. Благодаря этому два одновременных запроса одного пользователя не назначают два основных адреса в разных транзакциях в СУБД с поддержкой блокировок строк.
- Адрес выбирается исключительно из `$user->addresses()`. Существующая проверка владельца выполняется до записи; чужие адреса не меняются.
- Если удаляемый адрес связан с заказом, связь снимается только для заказов владельца; исторический `address_snapshot` заказа сохраняется.
- Не меняются маршруты, таблицы, миграции и контракты остальных подсистем.
- Гарантия действует в AddressController и при создании адреса в checkout: пользователь блокируется до записи заказа, адрес и основной флаг сохраняются в общей транзакции заказа. Иные прямые записи user_addresses должны использовать тот же механизм.
- Первый адрес пользователя, в том числе сохранённый при оформлении, становится основным. Если основной уже есть, новый адрес заказа его не заменяет. Адреса без пользователя не участвуют в выборе основного.

## Проверка

```bash
cd services/backend
php artisan test --filter='DefaultAddressBehaviorTest|AddressControllerTest'
```

Тесты проверяют создание первого/последующих адресов, явный выбор при сохранении,
отказ от одиночного снятия галочки, удаление и переназначение, сохранение снимка заказа,
восстановление исторических данных без основного, обратную совместимость
`/set-default` и невозможность изменить чужой адрес.

При ручной приёмке проверить две браузерные вкладки одного пользователя,
кнопку «Основной адрес» и обновление списка после удаления.
