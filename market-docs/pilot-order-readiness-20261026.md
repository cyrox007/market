# Аудит готовности пилота: Липецк, один магазин и один склад

> Исходный аудит до реализации. Текущее состояние локальных исправлений и контракт API: [pilot-checkout-implementation.md](pilot-checkout-implementation.md). Перечисленные ниже пробелы не следует трактовать как состояние после исправлений.

Дата: 26.10.2026. Проверены код и настройки production только чтением. Реальные заказы, банковские операции и отправка во внешний API не выполнялись.

## Требуемая модель

Покупатель подтвердил охлаждение 60 минут. Отсчёт от создания заказа, оплата не перезапускает его. В этот период публичный статус «В обработке у менеджера». Оплата и выполнение — разные состояния.

До дедлайна покупатель может отменить заказ. После дедлайна — только заявка в поддержку, не автоматическая отмена. Истёкший срок должен блокировать отмену даже при остановленной очереди. Истечение срока переводит заказ в «Собирается» и разрешает отправку в api.svetofor-mebel. «Собран» и «Собирается» — разные состояния.

## Подтверждённые блокеры

1. Нет состояния/дедлайна охлаждения, задания завершения периода, публичных подписей и политики отмены по времени. Наличный заказ создаётся accepted, онлайн — awaiting_payment. Оплата переводит заказ в accepted, после чего текущий canBeCancelled() запрещает отмену без учёта времени.
2. DispatchOrderSyncTo1C ставит отправку сразу после создания. DispatchOrderStatusSyncTo1C повторяет её при сменах статуса. Нет общего барьера охлаждения в dispatcher/job/batch-command.
3. Production: integration_1c.enabled=true, base_url пустой. SyncOrderTo1CJob логирует success=false, но не выбрасывает исключение: штатные повторы очереди не гарантируют доставку.
4. Production: около 2 838 997 заданий integration-1c на момент проверки. Выборка первой записи — SyncProductAndStocksFrom1CJob от 21.07.2026, последней — SyncOrderTo1CJob от 26.10.2026, attempts=0. Это не 2,84 млн заказов: очередь общая с импортом. Нужны диагностика обработчиков, отдельная очередь заказов и безопасный план обработки старого хвоста; массовая очистка не выполнялась.
5. Production: 0 магазинов, 0 профилей доставки, оба физических склада активны, самовывоз выключен, physical_site_id отсутствует. Пилот ещё не ограничен центральным складом Липецка LP00001 (id=1). Второй источник id=2 активен.
6. Production: методы raiffeisen_card и raiffeisen_sbp включены, но public_id/secret_key отсутствуют как в конфигурации, так и в методах оплаты; тестовый режим/хост pay-test.raif.ru. Боевая оплата не готова. Ключи не выводились.
7. Неоплаченный заказ автоматически отменяется через 10 минут: orders.unpaid_auto_cancel_minutes=10. Это отдельное правило, конфликтующее с описанным сценарием передачи неоплаченного заказа после 60 минут.
8. GET заказа и POST отмены защищены auth:sanctum. Гостевой заказ создать можно, но устойчивого самостоятельного просмотра/отмены для гостя нет. last_created_order_id используется для payment-config, не заменяет полноценный безопасный гостевой доступ. Привязка гостевого заказа по email требует отдельной проверки подтверждения личности.
9. Cancel endpoint проверяет статус без транзакционной блокировки вместе с изменением: нужно защищать гонки с оплатой, дедлайном и передачей. Отмена заказа не равна банковскому возврату; в админке возврат — отдельная операция.
10. POST /orders не имеет явной защиты Idempotency-Key. Повторное нажатие/сетевой повтор/две вкладки требуют устойчивого ключа оформления.
11. Нет специализированного сценария заявки на отмену после дедлайна. Админские кнопки смены статуса/принудительной отмены нужно согласовать с новой политикой и возвратом.

## Что означает «один клик» сейчас

POST /api/v1/orders/one-click только формирует direct_checkout (items, цена, submit_endpoint); заказ ещё не создаёт. Реальное оформление — POST /api/v1/orders с items. Отдельно есть OneClickLeadService для заявки менеджеру: не считать заявку полноценным заказом, резервом или оплатой.

## Контракт API, который нужно реализовать

Сохранить POST /orders, GET /orders, GET /orders/{id}, GET /orders/{id}/payment-config, POST /orders/{id}/cancel для владельца. Добавить безопасный гостевой доступ, привязанный к заказу (не доступ по одному номеру/email), и заявку на отмену после дедлайна.

В заказе явно отдавать: статус выполнения и публичную подпись, статус оплаты, cooling_until, server_time, can_cancel, can_request_cancellation, can_pay, состояние отправки во внешнюю систему, состояние возврата и заявки на отмену. Возможность отмены рассчитывает сервер, фронт только показывает её.

POST /orders должен поддерживать идемпотентность. Повтор того же оформления возвращает тот же заказ; тот же ключ с другими данными — 409. Переходы отмена/оплата/конец охлаждения должны быть атомарны. Внешняя отправка — после commit, с уникальным идентификатором заказа, подтверждением приёма, повторами и журналом ошибок. Нельзя обещать ровно однократную доставку без дедупликации у принимающей стороны.

## Матрица обязательных проверок

| Сценарий | Ожидание |
|---|---|
| Гость/пользователь × корзина/прямое оформление × наличные/карта | Один заказ с фиксированными ценами, складом и дедлайном |
| Неуспешная/брошенная/повторная оплата | Нет дубля заказа и ложного paid |
| Оплата в начале/конце охлаждения | Не переводит в сборку до дедлайна, не сбрасывает 60 минут |
| Отмена до дедлайна | Запрет отправки, однократный возврат резерва, возврат/void оплаты по правилам банка |
| Оплата приходит после отмены | Заказ не оживает; сверка и возврат либо ручная обработка |
| Отмена ровно на дедлайне | Единое правило: now < cooling_until; после — только обращение |
| Остановлен worker/cron | Отмена после срока заблокирована; сборка/отправка догоняются без дублей |
| Ошибка внешнего API/таймаут после приёма | Повтор с тем же внешним ключом, видимая ошибка, без двойного заказа |
| Недостаточный остаток/два покупателя последней единицы | Один успешный резерв, второй получает понятный отказ |
| Двойное нажатие/две вкладки/повтор запроса | Идемпотентное оформление |
| Чужой заказ/гостевая ссылка | Нет доступа, утечки контактов и управления чужой оплатой |
| Отмена в админке/поддержке после отправки | Контролируемый процесс, журнал оператора, синхронизация и возврат |
| Пустая корзина/архивный SKU/смена цены/услуги | Серверная проверка и понятное сообщение до списания |

## Порядок подготовки

1. Утвердить: поведение неоплаченной карты на 60-й минуте, смысл «одного клика», правила возврата оплаченного заказа.
2. Реализовать жизненный цикл и общий барьер внешней отправки, идемпотентность и безопасный доступ гостя.
3. Согласовать callbacks банков, автоотмену неоплаченных, резерв и админские операции; добавить тесты всей матрицы.
4. Отделить очередь заказов от импорта, проверить cron/workers, адрес внешнего API, авторизацию и дедупликацию принимающей стороны.
5. Настроить один магазин/площадку/склад LP00001, территории, тарифы, часы, самовывоз и доступность остальных источников. Цены не придумывать.
6. Настроить эквайринг в sandbox, проверить полный цикл без реального списания, передать фронту обновлённый контракт.
7. Отдельно согласовать контролируемый production smoke-test и правила возврата тестового платежа.
