# Состав заказа и связь с менеджером (пункты 8–9)

## Снимок строки заказа

В `OrderItem` добавлены `name` и `display`. При создании новой строки сервер сохраняет
`display_snapshot` из реального выбранного SKU. Переданный клиентом снимок не принимается.
Состав включает: name, parent_name, article (external_id выбранного SKU), sku,
colors (прежний формат ProductColorRow с element/solution/base_colors), materials,
configuration, specifications и данные комплекта bundle из ценового снимка.
Все названия/значения характеристик зафиксированы в JSON, не перечитываются из каталога
при просмотре. Собственное значение SKU перекрывает родительское по существующим правилам.
Цвета берутся именно у выбранного SKU, не из палитры соседних предложений.

`materials`, `configuration`, `specifications`: массивы `{slug, name, value}`.
Разделение материалов и комплектации задаётся явными slug в config/order_item_display.php;
атрибуты вариаций дополнительно входят в configuration. Полный набор выбранных
характеристик сохраняется в specifications. Физические размеры не подменяют комплектацию.
Для неизвестного материала можно дополнить material_slugs, не теряя сохранённые данные.

`display.source=snapshot` означает новые сохранённые данные; version=1,
captured_at — время фиксации. В старых заказах без снимка source=legacy, известное
сохранённое имя остаётся, colors/materials/configuration пусты. Текущие характеристики
карточки не выдаются за исторические. Автоматического заполнения старых заказов нет.
Снимок и product_id новой строки защищены от последующей подмены через модель.
Действующие поля product/price/quantity/total/bundle оставлены совместимыми.
Для отображения образцов фронтенд может использовать существующий ColorSample.
Копии медиа этим изменением не создаются.

Изменения публичного фронтенда в эту ветку не входят. Для интеграции фронтендеру
передаются display с сохранённым названием, цветами, подписями деталей, материалами
и комплектацией. Отсутствующая карточка каталога не мешает прочитать снимок через API.

## Контакты менеджера

`Order.manager_contact` в детали и ответе создания заказа содержит (в общий список
не добавляется, чтобы не выполнять поиск контактов для каждой строки истории):

```json
{
  "store_id": 17,
  "store_name": "Магазин в регионе",
  "phone": {"value": "+74742222222", "source": "regional_store"},
  "email": {"value": "info@example.test", "source": "global"},
  "hours": "10:00–18:00",
  "working_hours": [],
  "timezone": "Europe/Moscow",
  "actions": [
    {"type": "phone", "label": "Позвонить менеджеру", "url": "tel:+74742222222"},
    {"type": "email", "label": "Написать менеджеру", "url": "mailto:info@example.test?subject=..."}
  ],
  "primary_action": {"type": "phone", "label": "Позвонить менеджеру", "url": "tel:+74742222222"}
}
```

Приоритет магазина:
1. Активная выбранная точка самовывоза из зафиксированного fulfillment_snapshot.store_id.
2. Магазин населённого пункта из сохранённой адресной иерархии заказа (источник и ID ГАР/КЛАДР,
   без сравнения названий городов).
3. Активный магазин, связанный с сохранённым region_id заказа или его ближайшим предком.
   Несколько магазинов одного уровня упорядочены существующим priority, затем id.
4. Если подходящего магазина нет — глобальные ContactSettings.

Телефон и email проверяются и подставляются независимо: пустой региональный email не
мешает использовать региональный телефон плюс глобальный email. Неверный контакт
также не превращается в неработающую ссылку. Текущий регион браузера и клиентские
phone/email не используются. Неактивные магазины исключены.
В карточке магазина добавлены необязательные email и «Регион контактов»; телефон
теперь тоже можно оставить пустым для глобального fallback. Глобальные контакты берутся
из существующей страницы контактных настроек, без копирования значений в код.

primary_action — телефон, при его отсутствии почта; если нет обоих, null и actions=[].
Фронтенду следует скрывать кнопку при отсутствии контактов. Почтовая ссылка включает
номер заказа в теме. При наличии телефона и почты API отдаёт оба действия. Чат не задействуется.
Контакты читаются актуальными, а регион выбирается по самому заказу: смена телефона
магазина обновит способ связи и у старых заказов.

## Установка

Нужна миграция 2026_11_20_100000_add_order_item_display_and_store_email.
На локальном SERVER-AD:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File C:\OSPanel\home\svetofor.local\scripts\local\prepare-order-display.ps1
```

Журнал services/backend/storage/logs/order-display-setup.log, маркер ORDER_DISPLAY_SETUP_OK.
Миграция не меняет сохранённые строки старых заказов. Для Beget отдельное слияние,
и миграция. Сборка публичного фронтенда для этой ветки не требуется.
Изменения в данной ветке не выкладываются автоматически.
