# Вывод неиспользуемых информационных блоков товара из эксплуатации

## Решение и причина

Удалены **две старые редакторские подсистемы**:

- **«Фичи товаров»** (`ProductFeatureBlock`) — произвольные преимущества с иконками.
- **«Блоки доставки»** (`ProductDeliveryBlock`) — статический текст о доставке и сборке, назначаемый товару или категории.

React-карточка товара `apps/frontend/src/pages/product/ProductContent.tsx` не отображала эти блоки. До удаления `ProductDetailResource` вычислял их для каждого запроса карточки через `getForProduct` и дополнительные запросы к pivot-таблицам. Данные уходили через `feature_blocks` / `delivery_blocks`, но клиент их не использовал. Демонстрационный `ProductBlocksSeeder` также создавал маркетинговые обещания о сроках, бесплатной доставке и сборке, не связанные с тарифами и складским расчётом.

## Что выведено

- Пункты меню Filament и 14 связанных страниц, форм и таблиц двух ресурсов.
- Relation managers категорий и связи `Category::featureBlocks/deliveryBlocks`, `Product::featureBlocks/deliveryBlocks`.
- Две модели, их policy, factory и изолированные unit-тесты.
- Лишняя вычислительная работа в `ProductDetailResource` и поля `product.feature_blocks` / `product.delivery_blocks` в JSON карточки товара.
- Неиспользуемые интерфейсы TypeScript и свойства `ProductDetail`; поля удалены из OpenAPI.
- Демо-заполнение и упоминания в инструкции по seeders.
- Новые разрешения для этих ресурсов больше не создаются в `RolesAndPermissionsSeeder`; названия убраны из каталога разрешений.

## Что оставлено

**Не удалять** действующие модули доставки, сборки и подъёма: `shipping/quote`, `shipping/pickup-options`, `WarehouseDeliveryQuote`, `WarehouseDeliveryProfile`, `DeliveryHandlingType`, `AdditionalService` и реальные правила оплаты/доставки. Их данные используются в карточке товара, корзине и оформлении и принципиально отличаются от статических рекламных блоков.

Исторические миграции от 2026-01-21 и существующие **шесть таблиц** сохраняются в БД, без `DROP TABLE` и потери медиа:

- `product_feature_blocks`, `product_delivery_blocks`;
- `category_feature_blocks`, `category_delivery_blocks`;
- `product_feature_blocks_pivot`, `product_delivery_blocks_pivot`.

Это **архивные таблицы**, больше не используемые приложением. На рабочей БД их наполнение не проверялось. Перед отдельным удалением схемы нужно снять резервную копию, оценить количество записей и медиа Spatie, проверить потребителей старой версии API, затем оформить отдельную миграцию. Существовавшие ранее записи разрешений Spatie тоже могут остаться в рабочей БД; их удалять лишь после аудита назначений. Не запускать для этих блоков старый `db:seed`.

## Изменение API

В `GET /api/v1/products/{slug}` **больше нет** полей `product.feature_blocks` и `product.delivery_blocks`. Это целенаправленное удаление неиспользуемого контракта. Если существуют сторонние потребители этого API, перед выкладкой необходимо проверить их; при необходимости используется совместимая серверная версия до обновления клиента.

Поля `delivery_days`, `documents`, `colors`, `palette` и действующий API расчёта складов/доставки не изменяются.

## Контроль после внедрения

1. `ProductControllerTest`: карточка товара отдаёт остальные поля, а двух удалённых ключей в JSON нет.
2. В админке нет двух ресурсов «Блоки товаров»; категории сохраняют остальные relation managers.
3. Запрос товара не обращается к legacy-таблицам блоков.
4. Доставка/самовывоз/подъём/сборка рассчитываются как раньше по профилям и услугам.
5. Проверить тесты backend, OpenAPI и фронтенд CI. Реальное наполнение старых таблиц и сторонних потребителей API — ручная проверка до выкладки.
