# Продаваемый комплект: остатки компонентов на разных складах

## Правило владения остатком

Корневая карточка \`Шкаф + антресоль\` — группа цветовых торговых предложений. Выбранное цветовое предложение — виртуальная конфигурация. **Ни у корня, ни у цветового SKU комплекта не создаётся складской остаток или резерв.** Реальные номенклатуры — конкретные SKU шкафа и антресоли из подтверждённого состава соответствующего цвета. Количество товара в заказе умножает количество каждой составляющей.

Физический остаток и доступность каждого SKU определяются отдельно по действующим складам. Например, белый шкаф находится на складе А, белая антресоль — на складе Б. Комплект можно доставить, если у каждого SKU есть **свой достаточный источник с покрытием адреса**. Отсутствие одного компонента блокирует весь заказ, нельзя создать частичный резерв. Остатки одинакового SKU из разных складов для одной строки автоматически не объединяются.

## API: подготовка прямой покупки

\`POST /api/v1/orders/one-click\`:

\`\`\`json
{"bundle_id":100,"primary_sku_id":104,"quantity":1}
\`\`\`

В \`items[]\` backend возвращает физические SKU (например 201 шкаф и 301 антресоль), их количество и цену. Виртуальный SKU \`104\` **не** включается.

## API: доставка

\`POST /api/v1/shipping/quote\` с полным физическим составом:

\`\`\`json
{
  "directory_external_id":"house-guid",
  "bundle_id":100,
  "primary_sku_id":104,
  "bundle_quantity":1,
  "items":[
    {"product_id":201,"quantity":1},
    {"product_id":301,"quantity":1}
  ]
}
\`\`\`

Backend перепроверяет состав. Если единого склада нет, допускается мультискладская доставка при независимом покрытии адреса каждым источником. Пример \`selected\` (поля для краткости опущены):

\`\`\`json
{
  "multi_warehouse":true,
  "stock_mode":"multi",
  "warehouse_id":7,
  "delivery_cost":1000,
  "delivery_days_max":6,
  "items":[{"product_id":201,"quantity":1},{"product_id":301,"quantity":1}],
  "warehouse_allocations":[
    {"warehouse_id":7,"warehouse_external_id":"WH-A","stock_mode":"quantity",
      "items":[{"product_id":201,"quantity":1}],"transport_cost":400,"profile_id":10},
    {"warehouse_id":9,"warehouse_external_id":"WH-B","stock_mode":"quantity",
      "items":[{"product_id":301,"quantity":1}],"transport_cost":600,"profile_id":20}
  ]
}
\`\`\`

Цены доставки — сумма отдельных тарифов склада; порог бесплатной доставки применяется только к физическим SKU данного склада. Срок доставки всего комплекта — максимум сроков источников. Предварительная доставка рассчитывается как раньше; поля \`warehouse_id\` и \`profile_id\` на верхнем уровне означают **ведущий источник**, не все SKU. Fingerprint источников не раскрывается в публичном ответе, но сохраняется в заказе.

**Ограничения:** если источники не могут доставить по адресу, мультискладская отгрузка недоступна. Для мультискладского комплекта не считаются автоматически подъём, сборка или дополнительные услуги (запрос с ними не получает такой тариф); самовывоз требует, чтобы все компоненты были в одной точке. Никакая бесплатная передача между складами не подразумевается.

## API: заказ

\`POST /api/v1/orders\` принимает те же \`bundle_id\`, \`primary_sku_id\`, \`bundle_quantity\`, \`items\` вместе с обычными контактами, согласием, доставкой и оплатой. Сервер **повторно** строит комплект по выбранному предложению, пересчитывает цену и формирует собственный план распределения. Клиенту запрещено присылать \`warehouse_allocations\` или готовый снимок резерва.

Сохраняется \`order.bundle_snapshot\` (виртуальное торговое предложение, исходный состав, количества, цена) и \`order.fulfillment_snapshot.warehouse_allocations\` (склад и SKU на момент оформления). При создании заказа остатки разных складов блокируются в одной транзакции в фиксированном порядке. Если один склад изменился — весь заказ/резерв откатывается. \`cooling_until\` ведёт к резервированию без физического списания до подтверждения; при подтверждении уменьшаются \`quantity\` и \`reserved_quantity\` на исходном складе; при отмене освобождаются резервы на **тех же складах**, повторная отмена не меняет их второй раз.

Публичный \`OrderResource\` отдаёт структуру \`fulfillment\` с распределением при наличии соответствующего доступа; частные отпечатки складов и тарифов не выдаются наружу.

## 1С

Для односоставного источника сохраняется прежний контракт \`warehouseExternalId\` в заказе. При мультискладской отгрузке верхнеуровневое поле будет \`null\`, а у каждой физической позиции в \`products[]\` появляется \`warehouseExternalId\` её фактического источника. Виртуальная комбинация не передаётся отдельной товарной строкой. **Необходима проверка, что приёмник 1С поддерживает per-line warehouseExternalId:** без неё выкатывать мультискладские заказы на реальную 1С нельзя, иначе будет ошибка проведения. Если приёмник не поддерживает, потребуется обновить интеграционный контракт, а не передавать фиктивный общий склад.

## Безопасность и совместимость

- Старые заказы и одиночные товары используют прежний единственный \`warehouse_id\`.
- Новые мультискладские снимки неизменяемы и не назначают источник заново при отмене/возврате.
- Старые механизмы снятия/списания общего \`product.stock\` не используются для виртуального предложения комплекта.
- Одна строка SKU привязана к одному источнику; совместные остатки SKU в двух складах пока не дробятся для одного комплекта.
- Способ доставить комплект по одной цене/одним курьером с последующим перемещением на базовый склад требует отдельного управляемого процесса консолидации и тарифа; текущий алгоритм считает независимые отгрузки со складов.
- Фронтенд в этой доработке **не изменён**.
